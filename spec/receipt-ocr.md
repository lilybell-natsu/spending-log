# レシート読取機能 仕様書

作成日: 2026-08-22
ステータス: 実装完了(v0.7.1、`docs/index.html` に実装済み)。
実際のレシート写真での検証により、精度には現実的な限界があることを確認済み
(詳細は末尾の「10. 実写真での検証結果と既知の限界」「11. 手動トリミング機能」
「12. 桁区切りカンマの分断バグ修正」を参照)。

## 1. 目的・ユーザーフロー

現在の記録フローは「日付→大項目→小項目→金額(手入力)→メモ→記録」。
このうち金額入力の手間を減らすため、レシート画像から金額を自動読取する機能を追加する。

```
[レシート画像を読み込む] → [OCRで金額を読み取る] → [大項目・小項目を選択] → [記録]
```

- 入力/編集モーダル(`#entryModal`)に「レシート読込」ボタンを追加
- タップすると端末のカメラ起動 or 写真選択(`<input type="file" accept="image/*" capture="environment">`)
- 選択後、自動でOCRを実行し金額欄に候補値を自動入力
- **自動入力された金額は必ずユーザーが目視確認・修正できる状態にする(自動記録はしない)**
  読み取り精度は完全ではないため、金額欄への反映はあくまで「入力の補助」であり、
  その後の大項目・小項目選択、記録ボタン押下は既存フローのまま変更しない

## 2. 検討した方式と選定理由

| 方式 | 概要 | 採否 | 理由 |
|---|---|---|---|
| クラウドOCR API(Google Cloud Vision, Azure等) | 画像をAPIに送信しテキスト抽出 | ✕ | 本アプリはバックエンドなし(README記載の通りフェーズ2で検討)。クライアントのみの公開HTMLにAPIキーを埋め込むと第三者に抜き取られ悪用されるリスクがあり、個人開発の家計簿アプリの規模には見合わない |
| ブラウザ標準 Shape Detection API (`TextDetector`) | ブラウザ組込みのテキスト検出 | ✕ | 仕様が事実上非推奨・実装がChromiumの一部にしかなく、本アプリが重視するiOS Safariでは利用不可のため対象外 |
| **クライアントサイドOCR(Tesseract.js)** | 端末内(ブラウザのWASM)でOCRを実行 | **採用** | バックエンド不要、画像は端末外に一切送信されない(プライバシー面で家計簿アプリに適する)、iOS Safariでも動作する |

### 採用方式: Tesseract.js

- CDN経由で動的に読み込む(初回のレシート読込ボタン押下時のみ。通常のアプリ起動時にはロードしない=既存の軽量な初期表示を維持):
  `https://cdn.jsdelivr.net/npm/tesseract.js@5/dist/tesseract.min.js`
- 言語データは日本語(`jpn`)を指定して認識
- 画像・OCR処理は完全に端末内(ブラウザのWASM/Worker)で完結し、外部サーバーには一切送信されない

## 3. 動作検証(プロトタイプ)

日本語混じりの合成レシート画像(canvas生成、「小計」「消費税」「合計」「お預り」「お釣り」を含む)に対し、
実際にTesseract.jsでOCRを実行して検証した。

**入力画像の内容(抜粋):**
```
小計          ¥750
消費税(8%)     ¥60
合計          ¥810
お預り        ¥1,000
お釣り          ¥190
```

**OCR認識結果(抜粋、実行時間 約4.9秒):**
```
小計 \750.
消費 税 (8%) _\60
合計 \810
お 預り \1,000
お 釣り \190
```

**下記の抽出ロジックによる結果: `810`(正しく「合計」の値を抽出。小計750や
お預り1,000ではないことを確認)**

→ 日本語混じりのレシートでも、数字部分の認識精度は高く、キーワードベースの
抽出ロジックと組み合わせることで実用的な精度が得られることを確認した。
(文字部分の認識は完全ではない=店名や品目名の誤認識はあるが、金額抽出には影響しない)

## 4. 金額抽出ロジック(v0.6.1で座標ベースに変更)

初版(v0.6.0)ではOCRテキストの改行(行)単位でキーワード行を探す方式だったが、
ラベルと金額の間に大きな空白があるレイアウトで行がずれることがあり精度が低かった。
v0.6.1では、OCRが返す**単語ごとの座標(bbox)**を使い、「合計」の文言と**同じ行
(Y座標が近い)**にある金額を最優先で抽出する方式に変更した。
「一番大きい数字を採用する」のではなく、あくまで「合計の横にある金額」を優先する。

1. 全角数字を半角に正規化
2. `data.words`(Tesseract.jsが返す単語ごとの認識結果、各々`bbox:{x0,y0,x1,y1}`を持つ)
   から `合計` `合計金額` `総合計` `お会計` のいずれかを含む単語を探す
3. そのキーワード単語のY座標(中心)を基準に、同程度のY座標(同じ行とみなせる
   許容誤差内)にある他の単語を左から右の順に確認し、最初に見つかった
   金額らしい数値(10〜1,000,000の範囲)を採用する
4. 座標データが無い、または上記で見つからない場合のフォールバックとして、
   OCRテキストの改行(行)単位でのキーワード一致→それでも無ければ
   テキスト中の数値の最大値、という初版(v0.6.0)のロジックを使う
5. 該当なしの場合は金額欄を空のままとし、「金額を読み取れませんでした。
   手入力してください」を表示

```js
// 座標(bbox)ベースの抽出(最優先)
function extractAmountFromWords(words){
  if(!words || !words.length) return null;
  const rowCenter = w => (w.bbox.y0 + w.bbox.y1) / 2;
  const rowHeight = w => (w.bbox.y1 - w.bbox.y0);
  const keywordWords = words.filter(w => w.text && RECEIPT_KEYWORDS.some(kw => fullWidthDigitsToHalf(w.text).includes(kw)));
  for(const kw of keywordWords){
    const kwY = rowCenter(kw);
    const tolerance = rowHeight(kw) * 0.6 + 4;
    const rowWords = words
      .filter(w => w !== kw && Math.abs(rowCenter(w) - kwY) <= tolerance)
      .sort((a,b) => a.bbox.x0 - b.bbox.x0);
    for(const w of rowWords){
      const amount = parseAmountToken(w.text);
      if(amount !== null) return amount;
    }
  }
  return null;
}
```

### 検証結果(v0.6.1)

「小計¥1,200」「消費税¥96」「合計¥1,296」「お預り¥2,000」「お釣り¥704」を
ラベルと金額を大きく離して配置した合成レシート画像で検証。
**お預り(2,000)が合計(1,296)より大きい値であっても、正しく「合計」行の
1,296を抽出できることを確認**(単純な最大値採用ではないことの実証)。

## 6. データモデルへの影響

**なし。** レシート画像自体は記録データに永続化しない(OCR処理が終わったら破棄)。
理由:
- 既存のレコードスキーマ(`id/date/category/subCategory/amount/memo/createdAt/updatedAt`)を
  変更せずに済む
- 画像をlocalStorageにBase64で保存すると1件あたり数百KB〜数MBになり得て、
  localStorageの容量上限(ブラウザにより5〜10MB程度)をすぐに圧迫する
- 本機能の目的は「金額入力の手間を減らすこと」であり、レシート画像の保管・閲覧は
  別スコープ(将来必要になった場合はIndexedDB等への切替を伴う別機能として再検討)

## 7. エラーハンドリング・フォールバック

| ケース | 挙動 |
|---|---|
| オフライン(Tesseract.js本体・言語データがCDNから取得できない) | 「オフラインのためレシート読取は利用できません。手入力してください」を表示し、通常の手入力フローへ |
| OCRは成功したが金額が抽出できない | 金額欄は空のまま、「金額を読み取れませんでした。手入力してください」を表示 |
| OCR自体が例外を投げる | 同上のメッセージでフォールバック、`console.error` に詳細を出力 |
| 抽出した金額が明らかに不自然(例: 0円、上限超え) | 抽出ロジック内で除外(`10〜1,000,000`の範囲外は候補にしない) |

いずれの場合も、既存の「手入力して記録する」フローは常に利用できる状態を維持する
(レシート読取はあくまで補助機能であり、必須の経路にしない)。

## 8. 制約・既知の限界

- OCR精度は完全ではない(特に店名・品目名などの文字部分)。金額(数字)の認識は
  比較的精度が高いが、桁の誤認識等の可能性はゼロではないため、**自動入力後の
  ユーザー確認は必須**とする
- 初回利用時にTesseract.js本体+日本語学習データ(合計 数MB程度)をCDNから
  取得するため、回線状況によっては読込みに時間がかかる場合がある
- 現状のService Worker(`sw.js`)はCDN(cross-origin)リクエストを積極的に
  キャッシュする設定にしていないため、オフライン時はレシート読取機能自体が
  使えない(手入力へのフォールバックで対応。将来的にCDNアセットのキャッシュ
  対応を追加する余地はある)
- レシートのレイアウト(改行位置、フォント、感熱紙の掠れ等)によって抽出精度は
  変動する。「合計」の文言自体が読み取れない場合は数値を推測せず読取失敗とする
  (v0.6.2以降。詳細は10節を参照)
- レシートの背景(机の木目など)が写り込む写真では、背景がOCRのノイズ源となり
  「合計」自体が読み取れないことがある(10節の実写真検証で確認済み)

## 10. 実写真での検証結果と既知の限界(v0.6.1〜v0.6.2)

ユーザーより実際に撮影したレシート写真3枚(`C:\Users\harun\Desktop\Claude\receipt\`)を
提供いただき、これを使って精度検証・改善を行った。

### 発見した問題と対応

1. **「登録番号」欄の誤認識**
   インボイス制度の登録番号(例: `T3430010779376`、"T"+数字13桁)が、レシート上部に
   必ず印字されており、OCRがこれを金額と誤認して読み取ってしまうことがあった。
   → `isRegistrationNumberToken()`(T+数字のトークンを除外)と
     `isRegistrationLabelToken()`(「登録」「番号」を含む行/単語を除外)を追加し、
     座標ベース・テキストベース双方の抽出処理で登録番号を候補から除外するよう対応(v0.6.2)。
   単体テストで、登録番号が1トークンの場合・複数トークンに分割された場合の
   いずれでも正しく除外され、「合計」の金額を抽出できることを確認。

2. **「大きい数字」フォールバックの誤爆**
   キーワード(「合計」)に基づかない「テキスト中の数値の最大値を採用する」
   フォールバックが、実際のレシート写真では日付(例: 2026年→2,026円と誤認)や
   その他のノイズを誤って金額として採用してしまうことが実写真での検証で判明した。
   → このフォールバックを完全に撤廃(v0.6.2)。「合計」等のキーワードに基づく
     抽出で見つからない場合は、数値を推測せず「読み取れませんでした。
     手入力してください」とするよう変更。誤った数値を自動入力してしまうより、
     読み取れない旨を正直に伝える方が安全と判断。

3. **未縮小画像による処理時間の増大**
   スマホのカメラ写真(3000×4000px等)をそのままOCRにかけると、ローカル検証でも
   数十秒以上かかることが判明。
   → OCR前に長辺1600pxまで縮小する `downscaleImageFile()` を追加(v0.6.2)。

4. **画像の回転(向き)について**
   3枚とも横向き(90度回転)で撮影された写真だったが、ブラウザが画像読込み時に
   EXIFの向き情報を見て自動的に正しい向きで描画することを確認(`new Image()` +
   canvas描画の時点で既に補正済み)。そのため、アプリ側で追加の回転補正処理は
   **不要**と判断した(4方向で実際にOCRを比較し、無回転時が最も精度が高いことを
   確認済み)。

### 実写真3枚での最終結果(v0.6.2時点)

| レシート | 正しい合計 | 結果 |
|---|---|---|
| セイコーマート | ¥228 | 読み取れず(「読み取れませんでした」と正直に表示。誤った値は出さない) |
| ロピア | ¥5,445 | 読み取れず(同上) |
| サツドラ | ¥4,010 | ¥10 と誤抽出(「合計」行内で数字が一部だけ認識された) |

### 既知の限界(現時点の結論)

- 3枚とも、レシートが木目の机の上に置かれた状態で撮影されており、**背景の木目模様が
  OCRの強いノイズ源となり**、認識結果の大部分が意味不明な漢字風のノイズになって
  しまうことを確認した(二値化処理も試したが、背景と receipt の明暗差が
  一様でないため改善せず)
- この状態では「合計」という文言自体をOCRが正しく認識できないことが多く、
  キーワードベースの抽出ロジックを高度化しても限界がある
- 上記1〜3の対応により「誤った金額を確信を持って表示してしまう」リスクは
  大きく低減したが、「正しく読み取れる」ケースはまだ限定的
- **実用上の改善策**: レシートを無地の背景(白い紙・机など)の上に置く、
  影が入らないようにする、レシート部分が画面の大部分を占めるように撮影する、
  といった撮影条件の改善によって、OCR精度は大きく向上すると見込まれる
  (背景ノイズが今回確認できた最大の精度劣化要因のため)
- 将来的な改善案 → 11節の通り実装済み(v0.7.0)

## 11. 手動トリミング機能(v0.7.0)

### 検討: 自動トリミング vs 手動トリミング

10節の検証結果を受け、「レシート部分を自動検出してトリミングする」方式と
「撮影後にユーザーが手動でトリミングする」方式を比較検討した。

| | 自動トリミング | 手動トリミング |
|---|---|---|
| 実装 | エッジ検出・輪郭抽出等の画像処理が必要(OpenCV.js等の重いライブラリ、または自前実装は複雑・不安定) | ドラッグで矩形選択するUIのみ。標準的な実装パターンで軽量、依存ライブラリ不要 |
| 信頼性 | 背景の色・照明・レシートの折れ等で失敗しやすく、失敗時に気づきにくい | 人間が目で見て選ぶので確実。10節で判明した「背景ノイズ」問題を100%解消できる |
| 副次効果 | 背景除去のみ。「合計」の位置特定は別途必要 | 金額の数字だけを囲むようにトリミングしてもらえば、「合計」の位置特定すら不要になり、さらに精度が上がる |
| 既存設計との整合性 | - | 本機能はもともと「自動入力された金額を必ずユーザーが確認する」設計であり、もう一手間(トリミング)加えるのは自然な延長 |

個人利用の家計簿アプリという性質上、完全自動化より確実性を優先し、
**手動トリミング方式を採用**した。

### 実装内容

`docs/index.html`

- 新規モーダル `#receiptCropModal`: 選択した写真を表示し、四隅のハンドルを
  ドラッグして選択範囲(トリミング矩形)を調整できるUI
  - `.crop-mask`(上下左右4枚)で選択範囲外を暗くし、選択範囲を分かりやすく表示
  - Pointer Events(`pointerdown`/`pointermove`/`pointerup`)でドラッグ処理を実装。
    4隅のハンドルでリサイズ、矩形内部のドラッグで移動
  - 「この範囲で読み取る」ボタンで、選択範囲を元画像(ダウンスケール済みの
    作業用canvas)の画素座標に変換し、その部分だけを切り出した新しいcanvasで
    OCRを実行
- `extractSingleAmountCandidate(text)`: トリミングで範囲を絞り込んだ場合専用の
  最終フォールバック。候補となる数値が1つだけに絞れる場合のみ採用し、
  複数候補がある場合は推測しない(全体画像に対する「最大値採用」とは異なり、
  ユーザー自身が事前にノイズを除去済みという前提があるため安全)

### 検証結果

1. **座標変換の正確性**: 4色に塗り分けたテスト画像で、選択範囲を特定の色の
   領域に正確にドラッグし、「この範囲で読み取る」を実行した結果、切り出された
   canvasのサイズ・内容(中心ピクセルの色)が期待通りであることを確認
   (画素単位で正確に切り出せている)
2. **一連のフロー**: 合成レシート画像で、ファイル選択→トリミングモーダル表示→
   範囲確定→OCR実行→金額欄への反映→ステータス表示、モーダルのキャンセル時の
   リセット、まで一通り正しく動作することを確認
3. **実際のレシート写真での効果確認**: セイコーマートのレシート(10節で
   「読み取れませんでした」だったもの)に対し、「合計」行付近に範囲を
   絞ってOCRを実行したところ、正しい金額(¥228)の一部(末尾の「28」)を

## 12. 桁区切りカンマの分断バグ修正(v0.7.1)

### 問題
ユーザーより「¥4,010や¥5,445だと、カンマの後の10や445しか金額として
認識されていない」と報告。

### 原因
1. OCRが桁区切りカンマの前後に余分な空白を入れて認識することがある
   (例: "4,010" → "4, 010")。この場合、旧ロジックの正規表現
   `[0-9][0-9,]{1,}` は空白で区切られてしまい "4," までしかマッチせず、
   `parseInt("4")=4` は範囲チェック(10以上)で弾かれてしまう
2. 座標ベース抽出(`extractAmountFromWords`)では、同じ行の単語を
   **1つずつ個別に** `parseAmountToken()` に渡していたため、OCRが
   "4,010" を "4," と "010" という**別々の単語(bbox)**として認識した
   場合、"4," は範囲外で無視され、次の単語 "010" が単独で金額として
   採用されてしまっていた(これが「10」「445」だけになる直接の原因)

### 修正
- `collapseNumberFragments(text)`: 数字・カンマの間にある空白(改行を除く)を
  詰める関数を追加。`parseAmountToken()` の冒頭で適用し、上記1のケースに対応
- `extractAmountFromWords`: 単語ごとの個別解析をやめ、同じ行の単語を
  スペース区切りで1つの文字列に結合してから `parseAmountToken()` に渡すよう
  変更。これにより「4,」と「010」のように別単語に分割されていても、
  結合後の文字列 `"4, 010"` に対して `collapseNumberFragments` が効き、
  正しく `4010` として抽出できる
- `parseAmountToken`: カンマ区切りの数値パターンを優先的に探すよう変更
  (単純な数字列マッチより先に試す)
- `extractSingleAmountCandidate` にも同様に `collapseNumberFragments` を適用

### 検証結果
- `parseAmountToken('合計 ¥4, 010')` → `4010`、`parseAmountToken('合計 ¥5, 445')`
  → `5445`(修正前はそれぞれ`4`が範囲外で弾かれ`10`のみ採用、`445`のみ採用と
  なっていた事象を再現・修正確認)
- 座標ベース抽出で「合計」+「4,」+「010」が別単語(bbox)の場合も
  `extractAmountFromWords` が正しく `4010` を返すことを確認
- 既存の登録番号除外ロジック(11節)が壊れていないことを回帰確認
- 実際にTesseract.jsでOCRした合成画像(「合計 ¥5,445」)でも、一連の
  トリミング→OCR→抽出フローで正しく `¥5,445` が金額欄に反映されることを確認
