## 判明した誤認識パターン

### パターン1: ¥記号が「W」「Y」に誤認識される
ロピアのレシートで、太字・大きめフォントで強調された「¥5,445」を含む行を
OCRすると、¥記号の部分が以下のように誤認識された:

```
実際の印字: 合計 (税率8%対象額 ...) ¥5,445 ¥403
OCR結果の例:
  「W5.445)」
  「Y5.445)」
```

¥記号が"\"(バックスラッシュ)になるケースは想定済みだったが、"W"や"Y"に
なるケースは未対応だった。フォントが大きい・太字だと¥記号の縦棒が
アルファベットのように誤認識されやすいと考えられる。

**対応(v0.8.2)**: 金額検出の記号クラスに `W` `Y` を追加
(`extractAllAmountCandidates` 内 `/[¥\\WY][ \t　]*([0-9][0-9,.]*)/g`)

### パターン2: 桁区切りの「,」が「.」(ピリオド)に誤認識される
パターン1と同じ箇所で、桁区切りのカンマがピリオドとして認識されていた
(`5.445` であり `5,445` ではない)。

**対応(v0.8.2)**: 数値の区切り文字としてカンマだけでなくピリオドも許容する
よう、`collapseNumberFragments` と金額の正規表現を拡張
(`[0-9][0-9,.]*` のようにピリオドも桁区切り文字として扱う)

### パターン3: ¥系の記号自体が認識されない
サツドラのレシートでは、「4,010」という数値自体は正しく認識されているが、
直前にあるはずの¥記号がどの単語にも現れず、OCRテキスト上で完全に
欠落しているケースがあった:

```
OCR結果の例: 「13 時 4,010 人 力 リ 科」 (¥記号なし)
```

**対応(v0.8.2)**: ¥系記号が検出できなくても、桁区切り(カンマまたは
ピリオド)を伴う数値(`[0-9]{1,3}(?:[,.][0-9]{3})+` のパターン)は
金額の可能性が高いとみなし、候補に含めるようにした
(「候補を一覧表示してユーザーが選ぶ」設計のため、多少候補が増えても
実害が小さいことを活かした対応)

### パターン4(未解決・既知の限界): 数字そのものがカタカナ等に誤認識される
セイコーマートのレシートでは、「合計」という文言自体は正しく認識されて
いたが、その右の金額「228」が「スピ」のような無関係なカタカナに
まるごと誤認識されており、正規表現による後処理では原理的に復元できなかった。

```
OCR結果の例: 「合計 \ ス スピ」 (¥228 が跡形もなく別の文字になっている)
```

これは文字種の誤認識ではなく、OCRエンジンが元の文字(数字)を
正しく検出できていない(別の文字だと確信して読んでしまっている)
ケースであり、後処理のパターンマッチングでは対応不可能。
実用上は、この場合は候補一覧に正しい金額が出てこないため、
**手入力にフォールバックする**(既存のUIで対応済み)。

### パターン5: 密集した行・広いトリミング範囲はOCR精度が下がりやすい
ロピアのレシートで、「合計」「(税率8%対象額...)」「(内消費税等)」
「¥5,445」「¥403」が非常に近接して1〜2行に詰め込まれている箇所は、
広め(複数行相当)にトリミングするとOCRが混乱し、¥5,445を正しい形で
拾えないことが多かった。一方、その1行だけに絞ってトリミングすると、
安定して「W5.445)」のような(パターン1で対応済みの)形で認識できた。

**対応**: コード側の対応に加え、トリミング画面の案内文に
「候補に出ない/文字化けする場合は範囲をその行だけに絞る」旨を追記(v0.8.2)。
根本対応ではなく運用上の工夫だが、ユーザーが範囲を調整するだけで
安定して改善するため有効。

### パターン6: トリミング範囲を先に縮小した画像から切り出すと精度が下がる
実装上の問題として、画像全体を先に1600pxへ縮小し、その縮小画像から
トリミング範囲を切り出していたため、範囲を絞り込むほど文字が
不鮮明(縮小によるぼやけ)になり、かえってOCR精度が下がっていた。

**対応(v0.8.2)**: トリミング確定時に、表示用の縮小画像ではなく
**フル解像度の元画像**から同じ相対範囲を直接切り出すように変更。
範囲を絞るほど、その分だけ元画像の実ピクセルをそのまま活かせるように
なり、パターン5の「範囲を絞ると改善する」効果がより効きやすくなった。

### パターン7: 数字の「0」がアルファベットの「O」(オー)に誤認識される
v0.8.2で「サツドラの¥4,010は候補に正しく表示される」と一度結論づけたが、
実際にユーザーが試したところ「検出不能、または¥4・¥10といった断片」に
なってしまうケースがあると報告があった。あらためて実際のOCR結果を
確認したところ、以下のように数字の「0」がアルファベットの大文字「O」
(オー)に誤認識されていたことが判明した:

```
実際の印字: 合計 \4,010
OCR結果の例: 「疾 E。 紳 二 \ 人 4.O1O 唱 誕生」
```

「0」と「O」は字形が非常に似ているため、フォントや解像度によっては
OCRがどちらとして認識するか安定しないと考えられる。¥記号と数字の間に
無関係な文字(上記例では「人」)が挟まってしまう現象も併発しており、
これは¥記号ベースの候補検出(パターン1)だけでは救えないが、
パターン3(¥系記号が無くても桁区切り数値を候補に含める)と組み合わせる
ことで、O→0の変換さえできれば救済できることが分かった。

**対応(v0.8.3)**: `normalizeOhToZero()` を追加。数字を含む連続した並び
(数字・O・カンマ・ピリオドのみで構成される部分)の中に現れるO/oを
「0」とみなして置き換えるようにした。「OK」「OOO」のように数字を
一切含まない英字の並びは対象外とし、通常の文章中のOを誤って
書き換えないようにしている。

## 検証結果まとめ(v0.8.3時点)

| レシート | 状況 |
|---|---|
| セイコーマート(¥228) | 数字自体の誤認識(パターン4)のため引き続き認識不可。手入力へフォールバック |
| ロピア(¥5,445、行全体を広めにトリミング) | 候補に出ないことがある(パターン5、密集レイアウトの限界) |
| ロピア(¥5,445、その行だけに絞ってトリミング) | **候補一覧に ¥5,445 が正しく表示されることを確認**(ユーザーによる実機確認でも成功) |
| サツドラ(¥4,010) | パターン7の対応により、**候補一覧に ¥4,010 が正しく表示されることを実際のOCRパイプラインで確認**(候補には¥101・¥4等の無関係な副産物も混じるが、ユーザーが一覧から選ぶ設計のため実害は小さい) |

## 今後の指針
- パターン4(数字自体の誤認識)は後処理では解決できないため、
  今後さらに改善するなら「範囲を絞ってもらう」運用でのカバー、または
  画像の前処理(コントラスト強調等)やOCRエンジン自体の変更が必要になる
- 「一度直ったと結論づけても、別のクロップ範囲・別の条件では再発する」
  ことがある(パターン7がまさにこのケース)。修正後は実際のOCRパイプライン
  で複数パターンを再検証し、断定的な結論を急がないこと
- 新しい誤認識パターンに気づいた場合は、このファイルの「判明した誤認識
  パターン」に追記し、`docs/index.html` の `extractAllAmountCandidates` /
  `collapseNumberFragments` / `normalizeOhToZero` に反映すること
